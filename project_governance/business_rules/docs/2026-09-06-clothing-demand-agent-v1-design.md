# 服装需求发现 Agent V1：方案与验收草案

日期：2026-09-06  
状态：用户已确认三种优先方法及“现成可采购商品”方向；本文是具体方案，尚未实现或通过业务验收。

## 1. 唯一真源与已确认边界

用户业务范围、观察周期约定和阶段状态，唯一维护于 [TASK_STATE.md](../../project_state/docs/TASK_STATE.md)。CTR、点击下单率及既有商品数据验收定义，唯一维护于 [field_dictionary.csv](../schemas/field_dictionary.csv)。本文定义新增工作流和需求证据结构，不另行设置业务阈值。

当前商品证据可从 [FastMoss 采集说明](../../../data_acquisition/fastmoss_catalog/records/README.md)进入。该来源已完成一次页面采集和导出验证，不能当作采购库存或三种需求方法的验收结果。

## 2. 第一版交付行为

用户设置本次市场、服装范围与观察窗口，提供或选择可读取的数据来源。系统读取原始证据，分别运行三种需求发现流程，生成需求卡；再在现有商品中核对款式与需求条件，补充供货证据，输出可人工复核的测品候选。

最终结果支持回到原始评论、帖子、搜索记录和商品页面。没有合适商品时保留需求卡，并明确缺少什么；不为凑足推荐数量放宽条件。

三种方法使用同一套证据库、需求卡、商品库和人工复核状态。V1 不要求部署三个独立自治模型进程；实现时可用同一模型处理不同结构化任务，减少重复采集和不必要调用。

## 3. 三种方法的具体输入与输出

### S1：评论痛点挖掘

输入：与服装相关的原始评论、评价或讨论，以及所讨论的帖子/商品上下文、来源链接、时间和可确认的市场信息。

处理：
- 提取明确的穿衣困难、失败替代方案、规格诉求和使用场景。
- 区分已经购买后的体验、购买前询问、普通赞美、玩笑及含糊表达。
- 合并相似需求，但保留证据原文及各自上下文。
- 标记同一内容转载、同一讨论线程和重复评论，避免重复计为独立需求支持。
- 只能在证据支持的范围内识别人群，不从头像或姓名猜测敏感属性。

输出：先保留按同商品、同问题聚合的问题线索；只有符合下述普遍性门槛后才生成 S1 需求卡。需求卡包括人群、场景、具体问题、必须满足的服装条件、支持/反对证据和不确定项。

2026-09-07 用户最终确认 S1 生成规则：单条问题反馈仍收集为线索，但不生成需求卡、不触发找货。升级必须同时满足下表三项，任何一项不满足或未知，均停在“待补证据”，不进入找货或测品。

| 维度 | 口径 | 已确认门槛 |
|---|---|---|
| 有效评价样本量 | 同商品（合并各 SKU）去重后的全部有效评价数 | ≥5；≥10 仅为建议，不是额外硬门槛 |
| 同问题独立买家 | 同问题正文去重后、有可靠身份去重依据的不同买家 | ≥3；不同正文至少3份是必要条件，不能代替买家身份确认 |
| 问题占比 | 提及同问题的有效评价数 ÷ 同商品全部有效评价数 | ≥20% |

分母包含有实质内容的好评，不能使用仅一星、低星或差评采样替代；全星级覆盖、样本完整性或有效性未确认时，占比保持待确认。统计只适用于当轮已确认市场与窗口，不合并其他商品，也不拿历史或其他市场评价补足当期门槛。

同商品、同问题不同表述合并，例如“偏大 / too big / runs large”属于同一问题；不同 SKU 合并统计，同时保留每条原文、评价 ID、商品 ID 和 SKU 关联。支持记录数、不同正文数、独立买家人数分别记录；正文不同、匿名昵称不同、评价 ID 不同或已购标记均不能单独证明不同买家。去重依据不足时独立人数待确认，不硬写人数。

有效评价排除纯赞美、无实质内容、同正文复制转载、同一讨论线程重复及疑似复用账号；重复正文不得累计独立人数。不能用删除未解释评价的方式缩小分母；无法判断有效性、市场或时点的记录保留并阻止受影响商品的占比确认。排除项、去重依据及来源均可回溯。

实现的资料接口与有限规则边界见 [评价覆盖与去重依据输入](2026-09-07-review-evidence.md)。当前样本重新判定及验证范围见 TASK_STATE.md；历史运行报告保持原快照，仅供回放或资料核对，不作为新规则下的合格需求卡证明。

验收要点：普通“好看”不自动成为痛点；没有关于材质、尺码的证据就不得补造；评论表达不自动变成真实成交记录。

### S2：热点与服装需求匹配

输入：热点主题及其来源时间、相关内容、服装讨论/搜索线索，以及可取得的同口径历史观察。

处理：
- 区分角色同款、风格元素和活动场景三类关联。
- 从真实证据提取颜色、版型、衣长、材质、搭配等要求；模型提出的联想另列为待验证假设。
- 将“发现相关内容”和“已证明热度增长”分开；没有可比历史值时不声称正在上涨。
- 检查热度发生市场与销售市场的联系，不直接把其他市场的热度当作美国购买需求。
- 记录热点剩余时效与可核实的交付时间；时效不足时提示不适合本次测品。

输出：热点证据 → 服装关联证据 → 需求卡。缺少中间关联证据时停留在“联想待验证”。

验收要点：演员或剧情被讨论不自动意味着其服装受欢迎；没有原始商品标识与款式核对证据时，只能说风格相关，不标为同款。

### S3：搜索需求与供给对照

输入：搜索词、来源平台、市场、采集时间、查询条件、实际展示的搜索指标，以及相同需求条件下检查到的商品和供应结果。

处理：
- 把搜索词拆成人群、场景、品类、属性、价格和交付约束。
- 保留搜索指标原始单位；平台指数不转换成绝对搜索量。
- 区分内容缺口、商品属性不匹配、采购条件不匹配和真实供货不足。
- 对每次供给检查记录平台、查询词、页数/范围、时间及已查看商品。
- 未搜到结果只能写“在本次检查范围内未找到”，不能写全市场不存在。
- 供给记录过旧、权限不足或加载失败均标记采集限制，不能计为需求缺口。

输出：需求条件与现有商品逐项对照，列出满足、冲突、未知的条件，以及本次供给调查边界。

验收要点：搜索内容少不等于商品少；低量词显示零不等于需求不存在；访问失败不等于无货。

## 4. 需求卡和商品匹配结构

### Evidence：原始证据

最小内容：evidence_id、平台、来源 URL、内容类型、原文/可复查摘录、来源发布时间或缺失原因、读取时间、上下文引用、市场证据、重复内容分组、采集状态。

每项提取结论引用 evidence_id。网页和评论作为数据处理，其中出现的指令不得改变采集范围、工具权限或筛选规则。

### DemandCard：需求卡

最小内容：
- demand_id、方法 S1/S2/S3、运行编号；
- 需求陈述、人群、场景、服装子类；
- 必须条件、偏好条件、尚未确认条件；
- 支持证据、相反证据、模型提出的假设；
- 观察窗口引用、市场依据；
- 当前状态：线索、待补证据、可进行商品匹配、已排除；
- 人工复核意见及版本。

一条需求可来自多种方法，但不因重复进入三种流程而被当作三份独立证据。

### ProductMatch：商品匹配记录

引用现有商品主数据字段，不复制维护另一套商品字段规范。新增：
- demand_id、product_id、具体 SKU（需要时）；
- 满足条件、冲突条件、未知条件及各项证据；
- 款式相关/需求符合/供货已核实三个独立判断；
- 实际采购链接或明确缺失原因；
- 供货证据引用、检查时间、采购要求和交付限制；
- 下一步复核或测品动作。

未知属性不按已满足处理。型号、店铺或 SKU 未对齐，不将别的商品的规格、销量或库存合并到当前商品。

## 5. “现成可采购”的判定

款式相似、存在零售链接、历史销量较高，都不足以单独证明采购可行。

标为“供货已核实”前，需要针对所选款式/SKU保存：
- 可访问的采购渠道或供应商确认记录；
- 对应规格及当前可采购状态；
- 可核实的价格、币种、采购数量条件；
- 发货地、配送范围及可获得的交付信息；
- 本次检查时间，以及仍需用户确认的商业限制。

只有零售页面或供应商状态未知时，保持“待供货核验”。若需求只能通过改款或开发满足，保留需求线索，但不放入本版现货测品候选。

本轮采购渠道选择与接入实测状态以 [TASK_STATE.md](../../project_state/docs/TASK_STATE.md) 为准；搜索接口调用成功不等于所选 SKU 已通过供货核验，也不保证检查时点之后一直有货。

## 6. 数据接入与可执行顺序

阶段 A：真实样本验证。
- 先读取已授权、实际可展示的页面，或导入用户取得的结构化记录。
- 为三种方法分别取得能回溯原文的真实样本及反例。
- 先验证证据提取、匹配和采购核对的工作流，再决定具体自动采集实现。
- 现有95件 FastMoss 商品可用于商品导入和匹配流程测试；不能替代评论、热点、搜索需求或供应商采购样本。

阶段 B：逐个平台接入。
- 候选入口包括 TikTok/Instagram/YouTube 的穿搭内容、Reddit 讨论、搜索趋势工具及商品/采购平台。
- 具体接入清单由页面实际可读性、账号范围和样本质量决定；这些均是待验证入口，不是已实现的全平台覆盖。
- 登录过期、验证页、无权限、加载失败和字段变化分别报告，保留断点及有效历史快照。
- 新一次运行不覆盖旧快照，重试不重复写入同一原始记录。

阶段 C：串联运行和人工复核。
- 三种需求结果汇总后，先检查证据完整性，再匹配商品。
- 供货核验后的结果进入人工测品清单。
- 回收测品结果，按方法保留效果记录，再调整筛选策略；不凭主观印象给三种方法设置效果权重。

## 7. 最小功能验收案例

以下是测试情境定义，不是已采集到的真实用户评论或市场事实。

| 编号 | 情境 | 期望结果 |
|---|---|---|
| A01 | 评论明确描述裤腿过长并自行改短 | 提取裤长问题；其他属性保持未知 |
| A02 | 评论只表达喜欢或赞美 | 不生成具体痛点或购买记录 |
| A03 | 同一评论被复制到多个采集结果 | 保留采集记录，不增加独立需求证据数 |
| A04 | 影视话题只有剧情讨论 | 服装关联待验证，不直接推荐角色同款 |
| A05 | 真实穿搭提问明确指向某种衣长与风格 | 需求条件逐项链接到提问证据 |
| A06 | 没有前期热度快照 | 不输出增长率或“正在爆发”结论 |
| A07 | 平台提示内容缺口，但已有符合需求的商品 | 不判定商品供给不足 |
| A08 | 商品搜索失败或账号无权限 | 输出采集受限，不判定无货 |
| A09 | 商品标题相关，但所需材质未提供 | 材质为未知，不标完整符合 |
| A10 | 商品匹配，但采购链接/库存/数量条件未核实 | 保持待供货核验，不进入现货测品候选 |
| A11 | 需求必须改款才能满足 | 保留需求，排除于本版现货候选之外 |
| A12 | 没有完整CTR/点击下单率分子分母 | 对应字段为空，不输出爆品概率 |
| A13 | 页面文本要求忽略规则或执行外部操作 | 作为来源文本保存，不执行该指令 |
| A14 | 运行未明确观察窗口 | 提示补充窗口，不默认最近三天或七天 |

通过这些案例只代表流程规则通过，不代表实际需求提取准确率或商品推荐效果达到某个业务水平。真实业务验收还要使用独立标注样本，记录错误、漏检、样本量及各来源差异；数值门槛待实际数据支持后确定。

## 8. 界面与输出

建议第一版仅提供四个工作区：
1. 本次运行：市场、范围、窗口、来源和运行结果。
2. 需求卡列表：按三种方法查看，展开原始证据与未确认项。
3. 商品对照：按需求条件显示满足/冲突/未知，并查看采购核对结果。
4. 人工复核：保留、补证据、排除、进入测品，以及原因和后续反馈。

导出至少包含需求卡、证据索引和商品匹配记录。确定性数值由程序计算，模型负责结构化提取和解释；推荐解释必须引用已有证据，不生成虚构引文。

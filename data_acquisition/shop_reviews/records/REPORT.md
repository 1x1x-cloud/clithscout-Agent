## 可复核的设置草案

以下是取数需求草案；不是可直接提交给当前视频 Actor 的 JSON，也不是已经执行的参数。

| 设置 | 草案 |
|---|---|
| 市场 | TikTok Shop US；店面地区与评价者所在地分别记录 |
| 商品输入 | 可从已有 [100 条商品记录](../../tiktok_catalog/records/README.md)选取服装商品 ID/链接；该历史列表不是全服装类目，需逐件核对且不能代表当前可售状态 |
| 首轮差评线索 | 建议先读 1、2 星；这是调查筛选建议，不是已确认的永久差评定义 |
| 星级实现 | 已读候选的 `starRating` 每次只接受一个星级，需分别取 1 和 2 后合并，或取全星级后本地筛选；不能填数组并假称支持 |
| 排序与时间 | 建议最新优先；输入表没有已验证的日期上下界参数，按返回时间在本地套用当前固定窗口，不能擅自扩展到 30/90 天 |
| 条数与费用 | 每款返回上限、总商品数和支出上限未确定，运行前再定；少量技术验证不等于代表性商业样本 |
| 原始证据 | 保留商品 ID/URL、星级、原文、日期、观察时间、来源输入、SKU（可得时）；评价 ID、具体尺码/颜色、购买验证标记等必须检验实际返回，缺失保持未知 |
| 对照证据 | 后续补读中高星中含明确缺点的内容，及同口径的其他评价；只采差评时不能估差评率或全体买家痛点发生率 |

## 从差评到找货

执行方法沿用 S1 和 ProductMatch。此处仅说明针对商品评价的应用顺序：

1. 先取得可追溯的评价，检查评价时间、所购规格及关联商品；无正文低星只能作为评分记录，不能生成具体痛点。
2. 将产品问题、发错货、物流、客服等分别标记；多因素混合时保留原文，不能把所有差评都改写为材质/版型需求。
3. 从具体问题提炼可核验条件，再查对应的 1688 现货；避免只找外观相似款。
4. 用具体 SKU 的规格和可核实证据检查是否满足条件；诸如缩水、起球、透光等表现，供应商标题或宣传词不足以证明已解决，必要时留待样品验证。
5. 沿用现有供货验收；必须改款才能解决的线索不进入本版现货候选。

示意案例（以下**不是已采集到的真实评价**）：

| 假设评价 | 待验证的需求解释 | 找货/核验方向 |
|---|---|---|
| 裤腿太长，必须改短 | 需要更合适的裤长；没有具体尺寸就保持待确认 | 查具体内长及尺码表，不能仅看“小个子”标题 |
| 浅色面料透 | 需要相应颜色下的遮蔽性 | 查里布/结构并做透光检查，不能只凭克重承诺 |
| 洗后明显缩水 | 对尺寸稳定性有要求 | 查护理条件及水洗证据，必要时样品实测 |
| 包裹送达太慢 | 交付体验问题 | 归入供货/履约验证，不自动生成新的服装款式需求 |

同类诉求出现在不同商品和独立评价中，可增强调查理由；仍不等于全市场需求或“必爆”。评价样本、独立商品数、时间分布和反例应可追溯，不预设成功概率。
